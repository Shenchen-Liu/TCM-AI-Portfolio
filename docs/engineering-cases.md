# 工程实践案例｜问题定位与技术方案

[返回作品集](../README.md) · [系统架构](architecture.md) · [技术选型](design-decisions.md)

以下案例来自实际开发与联调，按**问题 → 目标 → 解决方式 → 结果**组织，重点说明技术决策和可核对的工程效果。

## 01｜视觉算法：文件式舌诊 Demo → 常驻推理 API

**S｜问题**：早期舌诊独立脚本接收本地文件路径，多个分类步骤各自加载模型权重并读取/预处理同一张图片；早期 API Demo 也通过上传落盘再调用脚本运行。这可以演示算法，但连续提供服务时有重复初始化和文件 I/O 开销。

**T｜目标**：不重训团队已有模型，改造输入、模型生命周期与接口，使多种视觉算法能稳定作为应用服务调用。

**A｜我的工程推进**：将舌诊预测路径整理为 FastAPI 常驻服务，利用启动生命周期预加载/预热模型；以进程内 `ModelManager` 复用模型实例，上传字节直接内存解码，一次预处理向多个分类模型复用；并将相关独立算法整理为多服务容器部署方案。

**R｜结果与证据**：原始舌诊脚本与新版 `main.py` / `model_manager.py` 可核对模型重复加载 → 常驻复用和文件路径 → 内存数据流的变化。开发阶段观察到代表性端到端业务调用**约 20 秒 → 约 3 秒**，但缺少同条件计时脚本和日志，故只作为**历史体验对比**，不宣称 P95、QPS、并发容量或某一项优化的独立贡献。

**技术取舍**：进程内单例不等于跨 Worker 共享模型；预热可能增加启动时间与显存占用。真正的高并发能力还需独立测试。

## 02｜双屏状态：患者观察端不能反过来驱动工作流

**S｜问题**：一度使用患者屏的 SSE `EventSource` 订阅会**推进 Graph** 的事件接口；浏览器默认断线自动重连，会使“订阅”被当作新的执行请求，出现无人输入时采集流程自动推进的异常。

**T｜目标**：让医助操作、业务状态和患者被动观察职责清楚，患者屏断线/重连不应产生任何新的业务动作。

**A｜方案**：区分**驱动业务执行**的接口和**只读阶段观察**接口，患者端改为订阅活动会话与只读进度；医助端通过独立的 HTTP/WS 控制路径推进工作流。Electron IPC 只负责本机窗口级动作，避免依赖某一个页面作为状态唯一来源。

**R｜结果与证据**：开发记录及现有患者端 `EventSource`、只读 SSE 路由和服务端会话控制逻辑能够对应这次修正。该案例证明的是**控制/观察隔离的架构改进**，没有将它包装成吞吐或延迟提升。

**面试关键词**：幂等、自动重连、副作用、会话唯一状态源、WS 与 SSE 分工。

## 03｜媒体预览：状态 API 不慢，为什么界面仍在等待？

**S｜问题**：连续采集时出现用户端预览没有新画面、医助历史回看等待的问题；单独查询业务状态 API 很快，无法解释页面卡顿。

**T｜目标**：保证状态控制和媒体预览各自获得连接资源，维持摄像头按会话共享，避免多模块重复打开同一设备。

**A｜方案**：结合真实问题记录定位到当时浏览器 **HTTP/1.1 同源长连接竞争**；前端为媒体预览和静态内容使用独立媒体入口，后台复用摄像头会话和帧缓冲，统一处理未就绪、非拥有者及无效会话等异常。

**R｜结果与证据**：现有前后端保留媒体入口分离设计，历史维护记录有现场问题排查，局部合成输入检查覆盖部分错误/传输分支。当前没有可复核的完整浏览器重测与前后延迟曲线，因此只说明**问题的定位与工程调整**，不填未经测量的百分比。

**技术取舍**：分流减少请求竞争，但增加媒体服务部署、连接恢复及资源释放的维护成本。

## 04｜多轮问诊：LangGraph 子图暂停与恢复

**S｜问题**：多轮问诊在某些恢复路径下重新进入子图入口，导致已经提取的字段、重试计数等会话工作状态被重置；也曾出现等待输入节点没有正确暂停、流程空转的问题。

**T｜目标**：能够在真正的患者回答与医助操作之间暂停并保留信息，避免一轮对话清空前面已采集结果。

**A｜方案**：核对主图/问诊子图的暂停点、检查点命名空间和恢复时的状态注入路径，区分新的会话启动与在已有子图内部续跑。字段增量通过状态归并，缺项及重试仍由规则判断。

**R｜结果与证据**：源码中能找到子图暂停与恢复、SQLite 异步检查点、规则路由及对应回归覆盖。本案例是对**有状态工作流恢复正确性**的工程修复；检查点不等于摄像头、数字人和真实设备资源的自动恢复。

**技术取舍**：LangGraph 提供状态/子图能力，但正确暂停恢复需要理解执行图和命名空间，比简单 `if/else` 有更高调试门槛。

## 05｜数字人交互链路：业务解耦与响应等待优化

**S｜问题**：交互涉及 VAD 判断说话结束、ASR 转写、LLM 字段提取/追问、TTS 合成和数字人播放。开发日志出现过 VAD 提前截断半句话、重新连接后再次提交完整语音，进而重复请求模型的现象；非流式提取和下一问生成也可能形成串行等待。

**T｜目标**：既让数字人自然地完成问诊与采集引导，又保证语音播报、阶段推进和设备动作不相互抢跑。

**A｜已开展的工程处理**：

- 复用 OpenAvatarChat 的数字人和语音链，通过 **FastAPI OpenAI 兼容门面**把数字人会话关联到业务 LangGraph，再由业务层连接 SGLang；
- 区分需要完整结果的 NLU 调用与回复侧的流式输出；采集引导在必要时等待数字人播报完成，降低过渡话术、倒计时和摄像头动作之间的时序冲突；
- 根据实际日志拆解 VAD/ASR、两次 LLM 调用及 TTS 的潜在等待，讨论过减少无谓串行和重复请求、复用连接等优化方向。

**R｜目前状态**：上述服务拆分、流式回复、会话关联和阶段同步在现有架构有实现依据；**整条数字人链路的端到端低延迟优化尚未形成可核对的前后测试结论**。不把拟采用的并行化/调用合并写成已落地成果。

**下一步验证**：对同一轮用户回答记录 VAD 封口、ASR 完成、NLU 返回、追问开始/完成、TTS 首包及播报完成的时间戳，分别统计正常与重分段场景，再选择优化方向。

## 06｜多组件部署：从能运行到可维护的服务

**S/T**：产品依赖前端、FastAPI、OAC、Qwen/SGLang 和多个视觉算法服务，运行环境和 GPU/模型资源不完全一致，需要单机部署和可排障的维护入口。

**A**：区分宿主机业务与前端、Docker 内的推理/OAC 组件；模型权重不进 Git 或普通镜像、通过本地路径挂载；部署脚本、健康检查、CPU/GPU 模式与版本化配置分别维护。

**R**：目前有部署配置、健康接口和历史联调/运维记录，可证明工程组织；不代表完整自动化交付流水线、生产级高可用或已完成高并发压测。
