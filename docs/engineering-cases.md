## 案例 A｜为什么使用双屏 Electron + WS/SSE

**问题**：患者端要持续显示数字人、字幕和采集进度；医助端要控制会话、接管、回看和标注。二者需要同一会话，却有不同操作权限。

**实现**：一个 Electron 应用创建两个窗口。业务后端维持唯一会话状态：医助操作经 WebSocket 发送指令并接收状态；患者端通过只读 SSE 订阅会话阶段；Electron IPC 负责本机窗口级操作。模型和音视频另由独立服务提供。

**为什么这样选**：避免双屏各自持有独立的业务真相。SSE 适合单向观察，WS 适合双向控制；本地 IPC 不能代替与后端服务的同步。

**重要迭代**：曾识别出观察端不应触发流程推进的问题，后来将业务驱动和只读观察分离。当前仍需持续验证断线重连、窗口失焦和设备资源一致性。

## 案例 B｜为什么采用 LangGraph

**问题**：多轮问诊字段必须累积，拍照要等待引导与确认，异常时还要暂停、重试、补采和人工处理。

**实现**：主图组织采集阶段，子图负责各阶段内部细节；使用 State、检查点和条件分支控制执行。问什么字段主要由预设规则决定，LLM 负责自然语言理解和表达。

**选择理由与限制**：显式状态和暂停/恢复比将所有流程写入单轮 Prompt 更可控，也比持续扩展零散回调更容易维护；但图嵌套与检查点恢复复杂，外部设备连接不会因为存在状态保存就自动恢复。

## 案例 C｜为什么采用本地 Qwen + SGLang + OpenAvatarChat

**问题**：语音数字人交互、LLM 信息提取、业务流程控制属于不同技术层；部署和排障需要分开。

**实现**：SGLang 以 OpenAI 兼容接口服务本地 Qwen；FastAPI / LangGraph 处理业务；OpenAvatarChat 负责语音和数字人链路。

**选择理由与限制**：可以分别部署和替换模型、业务与交互能力，便于按显存和硬件约束进行资源配置。现有方案不意味着整条语音链完全离线，也没有同条件的 SGLang/vLLM 性能对比。

## 案例 D｜为什么重构舌诊推理服务

**问题**：原始算法 Demo 重复读取图片、逐项建模并加载权重，难以支持连续 API 请求。

**实现**：FastAPI 服务启动时预加载并预热模型，进程内复用模型实例；图片上传后通过字节和内存数组传递，并统一返回结构化结果。

**结果和证据**：旧新版代码可核对模型生命周期变化；开发阶段代表性端到端业务体验约 **20s → 3s**。没有保存规范化基准测试记录，因此不表述为 P95、QPS 或严谨的因果拆解。
