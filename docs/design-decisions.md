# 关键技术选型与 Trade-off｜从算法 Demo 到完整工作站

[返回作品集](../README.md) · [系统架构](architecture.md) · [工程案例](engineering-cases.md)

本页不是技术栈清单，而是解释**业务约束 → 方案选择 → 当前实现 → 代价**。现有 TCM 仓库可以证实所采用的实现，但部分选型动机是基于工程事实和用户场景的事后归纳，**不代表历史上做过完整替代框架基准评测**。

| 核心选择 | 为什么选择当前方案 | 实现证据与限制 |
| --- | --- | --- |
| **Electron + Vue 双屏** | 在同一台工作站按患者/医助角色拆分展示与操作，复用前端技术并直接分配物理屏幕 | 一个 Electron 主进程、两个 `BrowserWindow`、显示器分配与窗口 IPC；窗口相互独立，不能靠 Vue 全局变量共享会话 |
| **FastAPI 统一会话中枢** | UI、数字人、Graph 和设备需要同一会话编号、控制与数据归属 | HTTP 路由、医助 WS 和观察 SSE；中心化便于协调，但多服务故障和资源回收需要额外处理 |
| **IPC / WS / SSE 按语义分工** | IPC 负责本机窗口，WS 负责医助双向控制/确认，SSE 负责患者只读状态观察 | 曾因患者端订阅驱动型 SSE 并自动重连导致错误推进；区分“驱动”和“观察”后更安全 |
| **LangGraph 而非单轮 Prompt** | 多轮问诊有字段累积，采集节点需等待、暂停、重采及人工接管 | 主图/子图、条件路由、检查点、暂停恢复可核对；嵌套恢复复杂，外部设备不能只靠 checkpoint 恢复 |
| **Qwen3.5-9B + SGLang** | 本地部署模型，OpenAI 兼容 API 能连接业务后端和数字人组件；在单机显存约束下调整推理配置 | Compose 有单卡 TP=1、FP8、上下文长度和静态显存比例等设置；未形成与 vLLM 的同环境吞吐/P95 基准 |
| **OpenAvatarChat 复用语音数字人** | 不从零重写 VAD、ASR、TTS 与数字人渲染，而把业务流交给 FastAPI/LangGraph | OAC 的 LLM 客户端通过兼容门面连接工作流；语音、业务状态跨服务同步复杂，TTS 存在外部服务依赖 |
| **媒体入口与会话级摄像头复用** | 视频长连接可能占用浏览器同源请求资源，多窗口重复打开相机会造成冲突 | 媒体入口分流、复用会话帧缓存；新增端口/资源生命周期及异常回收责任 |
| **算法常驻服务 + Docker Compose** | 早期文件式 Demo 的模型重复初始化与依赖分散影响服务交付 | FastAPI 启动加载和预热、进程内模型实例复用、内存图像输入；四组独立服务部署；非多进程全局单例 |
| **SQLite 异步检查点** | 单机原型阶段，持久化 Graph 会话历史且避免在异步节点中使用不兼容的同步 saver | 使用 `AsyncSqliteSaver`；不等于具有集群级容灾与多节点高可用 |

## 关键选择 1｜为什么 LangGraph + 规则 + LLM，而不直接让模型管理诊断？

当前首要任务是**安全、可复核地完成采集**。LLM 负责字段抽取、有限意图和提问表达；字段缺口和下一步目标主要通过确定性规则选定。Graph 明确记录阶段、消息和人工干预点。相比全自动模型规划，牺牲了一部分自由度，换取流程可解释、可暂停、可调试和医助可控。

值得深入追问的是：State 与短期会话信息如何区别于长期记忆？主图和子图为什么要分层？恢复时 checkpoint namespace 不正确为何可能丢失已收集字段？详见 [工程案例](engineering-cases.md)。

## 关键选择 2｜为什么双屏还要“网络通信”？

**双屏是同一台主机上的两个进程隔离的渲染窗口**，不是两台设备相互通信。业务状态不应该依赖某个页面是否还开着，因此两端都订阅后端会话；窗口级操作用 IPC，医助双向交互用 WS，患者只读观察用 SSE。SSE 自动重连虽方便，也必须保证观察端点没有推进业务的副作用。

**媒体链路不能简单复用全部业务请求入口**：连续预览/历史视频可能长期占据浏览器连接资源。一次真实迭代通过媒体入口独立和摄像头缓冲复用，降低业务控制与媒体流的耦合；没有可复核的统一提速比例。

## 关键选择 3｜为什么 SGLang，而不是 vLLM 或云端模型 API？

采用本地 Qwen 推理有利于统一部署边界和调用入口，通过 OpenAI 兼容协议供 FastAPI/OAC 业务链使用。当前部署使用 SGLang，可在容器和模型参数层管理启动、健康检查、显存与上下文。FP8、短上下文和关闭 CUDA Graph 等参数反映具体机器下的**运行资源取舍**，而不是声称这些设定对所有负载最好。

**不能据此断言 SGLang 性能优于 vLLM**；只有固定硬件、模型精度、上下文、并发数和计时方法，才能形成可靠比较。当前语音链路还含外部 TTS 依赖，因此“本地 Qwen”不等于“完整语音工作站全离线”。

## 关键选择 4｜为什么数字人 / 模型 / 业务后端要拆成服务？

把 ASR/TTS/动画渲染、LangGraph 业务状态和 Qwen 权重服务拆开，能够重用成熟框架、分别迭代和定位故障。代价是必须关联会话标识、处理流式/非流式响应、语音播报完成门控、资源超时与重连。系统为此增加了 OAC 与业务中枢之间的兼容门面，而不要求改造整个数字人框架来承载全部业务逻辑。

## 可作为下一轮工程优化的事项（未作为成果）

- 复用 LLM HTTP 客户端连接池、完善请求超时及取消路径；
- 分段测量 VAD、ASR、NLU、追问生成、TTS 和渲染耗时，再评估并行或合并调用；
- 对同样的模型、图片和服务器环境进行冷/热启动与端到端统计，补足历史优化的定量证据；
- 完善端到端设备资源回收、工作站恢复和真机联调验证。

> 工程选型的价值不在于术语数量，而在于能解释“选择解决了什么问题、带来什么代价、代码是否真的这样工作”。
