# 中医多模态 AI 智能采集系统｜AI 全栈工程作品集

**从科研算法 Demo 到可运行的双屏 AI 工作站与可复用推理 API。**

这是一份脱敏的个人工程作品展示，聚焦我在科研软件产品化过程中承担的**需求分析、软件架构、技术选型、跨模块集成、联调和交付推进**工作。实际实现结合 AI Coding、开源框架和团队协作，并非个人独立开发全部专业算法或硬件。

> 当前展示的是项目工程原型和技术实践，不是已获临床认证的自动诊断系统。视频与产品图片将在授权、脱敏后补充。

## 项目背景与交付范围

团队长期探索以客观四诊信息和医生经验支持中医辅助诊疗。研发早期已有若干独立的面舌视觉算法与设备原型，但缺少可以统一操作的交互、采集、复核与数据归档流程。

我的工作重点是把这些独立能力组织成**真实可用的软件产品原型**：

| 技术路线 | 负责的工作 | 当前成果 |
| --- | --- | --- |
| **ToB · 四诊采集工作站** | 产品流程与架构设计，患者屏/医助屏协同，语音数字人、多轮问诊、视觉采集、状态管理和媒体归档 | 已形成双屏软件原型、问诊与面舌采集等流程，支持医助监控、基础标注与人工接管；脉诊设备仍在独立调试和集成 |
| **ToC · 视觉算法服务化** | 统一算法 API 接口、模型生命周期管理、内存数据处理与容器部署 | 舌诊等模型由独立脚本向常驻推理 API 转化；形成多算法服务部署结构 |
| **数据标准化探索** | 组织中医特征归一与语义匹配思路，结合 LLM API、向量表示和人工复核 | 开展离线特征标准化和候选匹配工作；尚非已上线的自动诊断功能 |

技术栈：**Python / FastAPI、Qwen3.5-9B / SGLang、LangGraph、OpenAvatarChat、Vue 3 / Electron、Docker / Linux**。

## 关键工程决策

### 1. 双屏和跨模块协同

使用 **Electron 双窗口**分别承载患者交互和医助控制，但将业务会话统一放在 FastAPI 后端；医助控制使用双向 WebSocket，患者屏通过只读 SSE 观察进度。这样避免把两个界面当作独立业务状态源，并为断线重连、人工接管和设备协调留出统一入口。

### 2. LangGraph 管理可控的多阶段工作流

采用主图加采集子图组织问诊、视觉采集和会话暂停/恢复；状态和缺项检查由代码规则管理，**Qwen 主要负责语言理解、字段提取和自然问句生成**。当前不是让大模型自主诊断或决定全部检查动作。

### 3. 独立本地推理和数字人交互

用 **SGLang** 作为本地 Qwen 的推理服务，通过兼容接口连接业务后端与 **OpenAvatarChat** 数字人语音能力。业务逻辑不直接嵌进推理引擎或数字人框架，方便独立部署、问题定位和后续替换。此处不声称 SGLang 在基准测试中优于其他方案。

### 4. 从文件式算法 Demo 到常驻推理 API

早期舌诊流程按文件路径读图，多个识别步骤重复创建模型和加载权重。后续重构中，将模型加载/预热前移至服务启动，复用常驻实例，采用上传字节内存解码和单次预处理。开发阶段观察到**代表性业务链路约 20 秒 → 约 3 秒**，这是历史体验对比，缺乏标准化复测记录，不代表当前工作站耗时或并发性能。

## 当前边界与后续规划

已实现的重点是采集工作站工程原型及独立算法服务能力。**特征标准化与医生复核体系正在完善**；面向候选证候、证据缺口和医生个性化策略的辅助诊断 Agent 属于后续探索，不作为本版已交付成果。专业算法与传感硬件由项目团队共同研发，不能视为个人独立成果。
